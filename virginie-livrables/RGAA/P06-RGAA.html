RGAA-7-1-DIALOG-NAME-001 - Dialogue dont la référence de nom est absente

NC_CONFIRMEE Bloquant Critère 7.1 Test 7.1.1

Sélecteur : #cgu-ids-modal

Observation : aria-labelledby référence #cgu-ids-modal-title absent

  • La cible cgu-ids-modal-title n’existe pas.
Comparer le code observé et attendu

Preuve observée - RENDERED_DOM

<dialog id="cgu-ids-modal" class="fr-modal" aria-labelledby="cgu-ids-modal-title" role="dialog" data-fr-js-modal="true">
          <div class="fr-container fr-container--fluid fr-container-md">
            <div class="fr-grid-row fr-grid-row--center">
              <div class="fr-col-12">
                <div class="fr-modal__body" data-fr-js-modal-body="true">
                  <div class="fr-modal__header">
                    <button aria-controls="cgu-ids-modal" title="Fermer" type="button" class="fr-btn--close fr-btn" data-fr-js-modal-button="true">Fermer</button>
                  </div>
                  <div class="fr-modal__content"></div>
                </div>
              </div>
            </div>
          </div>
        </dialog>

Résultat attendu

<dialog aria-labelledby="dialog-title"><h2 id="dialog-title">…</h2></dialog>

Le DOM rendu n’est pas nécessairement le fichier source du dépôt.

Impact : La fenêtre ouverte ne possède ni nom accessible ni contenu utile pour comprendre les conditions à accepter.

Source : RGAA 4.1.2 - test 7.1.1

Recommandation : Charger le contenu avant l’ouverture et fournir un titre présent référencé par aria-labelledby.

Contre-test : Ouvrir le dialogue et contrôler son nom avec un lecteur d’écran.

Qualification : La modale CGU s’ouvre vide et référence cgu-ids-modal-title, identifiant absent. Le focus entre dans la modale mais aucun titre ni contenu ne permet de l’identifier.

RGAA-7-1-SCRIPT-ARIA-HIDDEN-003 - Composant scripté visible mais masqué aux technologies d’assistance

NC_CONFIRMEE Bloquant Critère 7.1 Test 7.1.1

Sélecteur : #search-input

Observation : Contrôle scripté focalisé à la tabulation 10 sous aria-hidden=true

  • Le composant scripté visible ne restitue pas correctement ce contrôle aux API d’accessibilité.
Comparer le code observé et attendu

Preuve observée - KEYBOARD_TRACE

<input class="fr-input" name="query" aria-describedby="search-input-messages" placeholder="Rechercher" id="search-input" type="search" style="">

Ancêtre masqué:
<form action="/recherche" method="get" class="fr-search-bar" id="search" role="search" aria-hidden="true">
								<label class="fr-label" for="search-input">
									Rechercher
								</label>
								<input class="fr-input" name="query" aria-describedby="search-input-messages" placeholder="Rechercher" id="search-input" type="search" style="">
								<div class="fr-messages-group" id="search-input-messages" aria-live="polite"></div>
								<button title="Rechercher" type="submit" id="search-btn" class="fr-btn">Rechercher</button>
							</form>

Résultat attendu

<div role="dialog"><form role="search">…</form></div>

Origine de la preuve : KEYBOARD_TRACE. Elle ne constitue pas du code source applicatif.

Impact : Le champ et le bouton visibles peuvent être absents de l’arbre d’accessibilité.

Source : RGAA 4.1.2 - test 7.1.1

Recommandation : Synchroniser aria-hidden avec l’ouverture et l’exposition réelle de la recherche.

Contre-test : Ouvrir le composant au clavier puis contrôler simultanément le focus, le DOM et l’arbre d’accessibilité.

Qualification : La recherche visible conserve aria-hidden=true et ses deux contrôles sont atteints au clavier.
